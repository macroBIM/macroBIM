# 규칙 — 앱이 내놓은 파일은 파일 생긴 대로 그린다

영상이 `Save BOQ` 나 `Save DXF` 를 보여줄 때, 화면에 나오는 것은 **그 파일을 열었을 때
보이는 것**이어야 한다. 예쁘게 다시 조판하지 않는다.

| 대상 | 그리는 도구 | 무엇을 읽는가 |
|---|---|---|
| BOQ 워크북 | `tools/xlsxpreview.js` | 열 너비·행 높이·글꼴·채우기·테두리·정렬·표시형식 |
| DXF | `tools/dxf2svg.js` | LINE / CIRCLE / SOLID / TEXT 와 레이어 |
| 입력 시트 | `tools/mkparampage.js` | 셀 값과 서식, Excel 의 넘침 규칙까지 |

스플라이스 영상 첫 판에서 BOQ 를 HTML 문서로 다시 조판했다 — 큰 제목, 자체 열 너비,
대문자 라벨. 보기에는 정돈됐지만 **영상이 주장하는 바로 그 한 가지에 대한 거짓말**이다:
"버튼을 누르면 이게 나온다" 고 해놓고 나오지 않는 것을 보여준 셈이고, 첫 홍보영상이
제대로 그린 것과도 어긋났다. 영상마다 같은 파일이 다르게 보이면 안 된다.

## 스타일·포맷은 먼저 묻는다

사업이 시작됐으므로 출력 포맷은 **고객과의 약속**이다. 아래에 해당하는 것을 바꾸기
전에는 반드시 확인을 받는다 — 더 나아 보인다는 이유로도 바꾸지 않는다.

| 무엇 | 포함되는 것 |
|---|---|
| BOQ 워크북 | 시트 이름·순서, 머리행 문구, 열 순서, 숫자 표시형식, 색·글꼴 |
| DXF | 레이어 이름, 블록 구성, 치수 스타일, 파일명 규칙 |
| 입력 시트 | 키워드 목록, 각 키워드의 칸 순서, PARAM 시트 배치 |
| 예제 워크북 | 서식, 열 너비, 안내 문구 |
| 앱 화면 | 배치, 색, 글꼴, 버튼 이름 |
| 영상 | 자막 카드, 타이틀, 로고, 화면에 파일을 그리는 방식 |

바꿔야 할 이유를 찾았으면 **바꾸지 말고 물어본다.** 고쳐도 된다는 답을 받은 뒤에
고치고, 무엇을 왜 바꿨는지 커밋 메시지에 남긴다.

# 홍보영상용 시트

영상 촬영에만 쓰는 파일입니다. Example 메뉴에는 올라가지 않습니다.

| 파일 | I106 | 결과 |
|---|---|---|
| `PLATE3D_VIDEO_30M.xlsx` | 5 | 297 부재 · 20,018.017 kg · 30 m |
| `PLATE3D_VIDEO_54M.xlsx` | 9 | 497 부재 · 33,141.593 kg · 54 m |

`PLATE3D_PORTAL.xlsx`와 같은 창고인데, 함께 움직여야 하는 네 칸 중
세 칸을 첫 칸에 대한 **수식**으로 바꿔 놓았습니다.

```
I106  = 베이 수          ← 사람이 건드리는 유일한 칸
I109  =I106-1            도리·외피 복사 수
F112  =6000*(I106-1)     끝단 가새 위치
F115  =6000*I106         박공 기둥 위치
```

PLATE3D는 수식이 아니라 **엑셀이 저장해 둔 계산 결과**를 읽습니다
(`plate_builder_test.js` 의 `cellVal`). 그래서 `I106`에 9를 넣고 저장한 뒤
다시 불러오면 열 개 프레임짜리 54 m 창고가, 도리·가새·박공까지 제자리에
붙어서 나옵니다. 30M 파일은 원본 `PLATE3D_PORTAL.xlsx`와 부재 수·중량이
소수점까지 같습니다 — 수식으로 바꾼 것이 모델을 건드리지 않았다는 뜻입니다.

## 촬영

30M 을 먼저 불러온 뒤 **뷰 버튼을 누르지 말고** 54M 을 불러오세요.
첫 시트만 화면에 맞춰지고 그 뒤로는 시점이 유지되므로, 건물 앞쪽 끝은
제자리에 있고 뒤로만 뻗어나갑니다. 뷰 버튼을 누르면 다시 맞춰져서
늘어난 느낌이 사라집니다.

엑셀과 실시간 연동은 아닙니다. 저장한 뒤 Load Excel 을 다시 눌러야 합니다.

## 가설은 연출이 아니라 86장의 워크북입니다

9·10 번에서 자라는 것은 부재를 숨겼다 보였다 한 것이 아닙니다. **각 프레임이
엔진이 진짜 시트에서 지은 진짜 모델**이고, 파일이 86장입니다.

`tools/make_ggb.js` 에 스위치 둘을 붙여 만듭니다 — 모델도 하나, 생성기도 하나:

| 스위치 | 뜻 |
|---|---|
| `PARTS=twr,mcb,hgr,trs,dk` | 어느 조립체를 배치할지. 배치 안 된 모듈은 정의만 되고 안 그려진다 |
| `STAGE=<트러스>,<바닥판>` | 주탑에서 얼마나 나갔는지 0~1 |

**한 경간은 그것과 주탑 사이의 경간들이 다 선 뒤에야 존재합니다.** 중앙에서
바깥으로 자라는 시퀀스는 아무도 지어 본 적 없는 것의 그림입니다.

두 스위치를 다 비우면 **출하되는 `PLATE3D_GGB.xlsx` 와 행 내용이 완전히
같습니다.** 414행을 대조해 확인했고, 이게 이 변경의 조건이었습니다 — 영상
때문에 손님이 받는 파일이 달라지면 안 됩니다.

## 도면 컷이 텅 비었던 이유

첫 판은 프레임이 거의 다 백지였습니다. 두 가지가 겹쳤습니다.

`ggb_dxf.html` 이 svg 에 제 크기를 정하게 뒀습니다 — `width:100%; height:auto`.
일반도처럼 가로로 긴 창을 주면 브라우저가 1080 px 페이지 맨 위에 **120 px
짜리 띠**로 그립니다. **중앙부가 빈 것이 아니라 중앙부가 없었습니다.**

그리고 창을 시트 높이의 분수로 잡았습니다(`[0,0.16]`, `[0.02,0.075]` …).
시트는 3,785,154 단위 높이에 **축척 두 가지**의 도면 아홉 장이 쌓인 것이라,
분수는 도면이 아니라 종이의 아무 데나 짚습니다.

지금은 페이지가 1920×1080 에 고정(`preserveAspectRatio` + 프레임 밖 클립)이고,
`prep_ggb.js` 가 **도면마다 잉크의 실제 범위를 재서** `ggb_frames.json` 을
씁니다. 아홉 장이 아홉 프레임입니다.

**주행 컷은 트러스가 아니라 일반도입니다.** DXF 는 선 굵기를 시트 기준으로
정하므로 1:5000 에서 트러스 현재 선 하나가 트러스 깊이의 28 % 입니다 — 당길수록
격자가 아니라 빗금 막대가 됩니다. 일반도는 2 km 에 340 m 라, 프레임 높이로 잡고
지나가면 주탑·케이블·행어·경간 중앙이 차례로 옵니다.

**아홉 중 둘은 시트에서도 진짜로 비어 있습니다.** `VIEW md.twr FRONT/TOP` 은
모듈이 놓인 자리마다 그리므로 1:500 으로 주탑 둘을 1,280 m 떨어뜨려 그립니다.
영상은 잉크를 x 로 뭉쳐 보고 빈 구간이 도면 높이의 2.5배를 넘으면 갈라서 한
기만 잡습니다 — **출하 워크북은 안 건드렸습니다.**

## 끝의 여섯 컷은 들어간 것입니다

12·13 이 나온 것(도면과 수량), 14 가 들어간 것(입력 시트 414행), 15 가 어디서
받나(앱의 Example 목록), 16 이 와서 해봐라. 앞의 열한 컷이 다리를 보여 주고
뒤의 여섯 컷이 **그게 파일 한 장이었다**고 말합니다.

14 번 시트는 `mkparampage.js` 가 **출하 워크북에서 셀 단위로 읽은 것**입니다.
화면의 행 번호가 파일의 행 번호입니다. 새로 붙인 `FITW` 모드가 폭에만 맞추고
높이는 두므로, 414행을 1080 px 안에 뭉개는 대신 읽는 크기로 팬합니다.

15 번에는 자막을 안 얹었습니다. 패널이 *Example workbooks*, 줄이 *Golden Gate
Bridge*, 버튼이 *DOWNLOAD* 라고 이미 쓰여 있습니다 — 그 위의 카드는 화면을
소리내어 읽는 두 번째 목소리이고, 목록을 안 가리는 자리도 없습니다.

## 자막은 그림자가 아니라 판 위에 얹습니다

첫 조립에서 12·14 번 자막이 안 보였습니다. 흰 글씨에 부드러운 그림자는 어두운
뷰포트 위에서는 읽히지만 **흰 종이 위에서는 사라집니다** — 그리고 이제 이
영상의 절반이 흰 종이입니다(도면 시트와 입력 탭). 자막 상자에 반투명한 어두운
판을 깔았습니다. 종이 위에서 흰 글씨를 받칠 만큼 진하고, 3D 컷에서는 모델이
비칠 만큼 옅습니다.

## 카메라를 피하지 않고 지정합니다

앞의 영상들은 엔진이 로드마다 화면을 다시 맞추는 것을 피하려고 **View 버튼을
안 누르는 방식**으로 버텼습니다. 여기서는 `video_page.html` 의 `__aim` 으로
**로드가 끝날 때마다 같은 값으로 다시 조준**합니다. 86장이 한 프레임도
어긋나지 않습니다.

세 카메라는 계산이 아니라 **보고 골랐습니다**(`tools/aim_ggb.js`):

| 컷 | target | dist | az | el |
|---|---|---|---|---|
| 2 조감도 | `0, 0, 98000` | 1,950,000 | −62 → −38 | 19 → 26 |
| 6–10 가설 | `0, 0, 125000` | 1,050,000 | 85 | 4 |
| 11 히어로 | `640080, 0, 165000` | 360,000 | 55 → 70 | −4 |

처음 적었던 `dist 2,400,000 · el 16` 은 틀렸습니다 — 멀리서 위에서 보면
2.3 km 짜리 납작한 물건은 선 하나가 됩니다.

## 도장은 한 가지 주황이 아닙니다

International Orange 인데 **다섯 단계로 나눴습니다.** 전부 한 톤이면 9 번에서
트러스가 나가는 것이 보이지 않습니다. 주탑이 제일 짙고, 케이블이 밝고,
트러스는 그보다 밝고, **바닥판이 제일 밝습니다** — 마지막 컷에서 전진하는
것이 바닥판이기 때문입니다.

색은 시트에 없습니다. 엔진이 팔레트를 읽은 순서대로 나눠 주고, 바꾸는 곳은
좌측 목록의 스와치뿐이며, 그 선택은 파일에 남지 않습니다. 촬영 스크립트가
로드마다 같은 함수를 부릅니다.

## 음악은 그림을 건드리지 않고 붙입니다

`tools/score.js` 가 별개의 패스입니다. 조립기는 **무음 마스터**를 내고,
음악은 그 위에 스트림 복사로 얹습니다.

```
node tools/score.js PLATE3D_EIFFEL.mp4 <track.mp3>
```

- **그림을 다시 인코딩하지 않습니다.** 곡을 바꿔 두 벌 만들어도 어느
  쪽도 한 세대 내려가지 않고, 한 번 붙이는 데 몇 초입니다.
- 무음 마스터는 `*_mute.mp4` 로 남깁니다. 조립기를 다시 돌리거나
  다시 붙이다가 어느 쪽도 잃지 않습니다.
- 곡에 세 가지를 합니다. **자릅니다**(그림보다 길면 마지막 프레임에서
  악구 중간에 끊기는데, 그건 음악이 없는 것보다 나쁩니다). **양끝을
  페이드**합니다(대부분의 곡은 첫 샘플부터 만렙이라 타이틀 카드에
  따귀처럼 들어옵니다). **−15 LUFS 로 맞춥니다**(유튜브가 −14 근처로
  정규화하니, 여기서 내려 두면 파일이 말하는 소리가 아니라 보는 사람이
  듣는 소리를 듣게 됩니다).

### 곡이 짧으면 잇습니다 — 아무 데나가 아니라 컷 위에서

골든게이트는 2:43 이고 붙인 곡은 2:08 입니다. **35초가 빕니다** — 입력 시트,
초대 문구, 받는 장면, 로고. 끝이 통째로 무음인 영상은 절제로 안 들리고
고장으로 들립니다.

```
LOOP_AT=105 LOOP_TO=46.5 XF=3 node tools/score.js PLATE3D_GGB.mp4 <track.mp3>
```

`LOOP_AT` 에서 곡을 떠나 `LOOP_TO` 로 돌아오고 `XF` 초 동안 겹칩니다.
**0 초로 돌아오지 않습니다.** 인트로를 다시 트는 것은 아무도 루프 말고
다른 것으로 듣지 않습니다. 두 지점은 곡을 재 보고 고릅니다:

- **떠나는 곳은 곡 자신의 페이드 앞.** 이 곡은 119 초부터 스스로 잦아들고
  124 초부터 무음입니다. 그러니 105 초에 떠납니다.
- **돌아오는 곳은 골 뒤의 섹션 머리.** 이 곡은 46-47 초가 골(.40 .29)이고
  48 초부터 다시 꽉 찹니다. 46.5 에서 들어오면 크로스페이드 동안 앞이
  잦아드는 자리에 뒤의 조용한 두 마디가 겹치고, 그 다음에 섹션이 들어옵니다.
  **이음매가 실수가 아니라 전환으로 들립니다.**

**그리고 이음매를 그림의 컷에 맞춥니다.** 이게 진짜 판단입니다. 도면 컷이
102.0 초에 시작하므로 `LOOP_AT` 을 105 로 두어 3초 크로스페이드가 **102.0 에
끝나게** 했습니다. 음악이 도면 컷 직전에 꺼졌다가 컷과 함께 들어옵니다.

덤으로 곡의 브레이크다운(원본 75-91초)이 필름 130-147초에 앉습니다 — **입력
시트를 훑는 구간**, 영상에서 제일 조용한 그림입니다. 그리고 148초에 다시 꽉
차면서 초대 문구와 받는 장면을 밀어 올립니다. 이건 노린 게 아니라 두 지점을
고르고 나서 재 보니 그렇게 된 것인데, **재 봤기 때문에 알았습니다.**

확인은 귀가 아니라 자로 합니다. 붙인 뒤 출력의 초당 라우드니스를 다시 재서
**0 인 초가 하나도 없는지**(구멍), 그리고 골과 정점이 예상한 자리에 있는지를
봅니다.

### crf 는 화질이 아니라 배송 예산입니다

파일이 30 MB 안에 들어가야 하면, **음악이 앉을 자리를 그림에서 미리
비워 둡니다.** 에펠은 crf 24 에서 무음 28.6 MB 였고 음악을 붙이니
31.2 MB 로 넘어갔습니다. 25 로 올려 무음 25.0 MB · 음악 포함 27.6 MB.
격자와 검정 배경에서 24 와 25 의 차이는 안 보입니다. 조립기의 `CRF=` 가
그 손잡이입니다.

## 다른 오리진의 iframe 은 한 프레임 늦게 찍힙니다

앱을 사이트 안에서 찍으면 Chromium 이 그 프레임을 **별개의 프로세스**로
돌립니다. 그래서 `page.screenshot()` 이 프레임의 DOM 보다 한 페인트
뒤처질 수 있습니다 — DOM 은 `saved` 인데 사진은 `download` 이었습니다.
같은 순간, 두 프로세스.

프레임 안에서 `requestAnimationFrame` 두 번, 밖에서 한 박자 쉬고 나서
셔터를 누릅니다. 그러면 둘이 일치합니다.

## 썸네일

```
node mkthumb.js ggb
```

앞의 넉 장과 같은 판이되 **판이 둘**입니다. 교습 편은 기울어진 흰 카드
(`card`), 이 편은 **풀블리드**(`bleed: true`) 입니다 — 640 px 카드 위의
2.3 km 짜리 다리는 실 한 오라기이고, 화면 전체를 대각선으로 가로지르면
그게 그림입니다.

**대각선인 것은 취향이 아니라 산수입니다.** 다리 전체가 들어와야 하고 화면이
16:9 이므로 쓸 수 있는 가장 긴 선이 모서리에서 모서리입니다. `az −45 · el 34`
가 잉크의 바운딩 박스를 1.81:1 로 내놓고, 그걸 16:9 로 자르면 하늘이 거의
남지 않습니다. 더 당긴 각은 전부 반대편 주탑을 잃었고, 더 눕힌 각은 다리를
화면 가운데 띠로 만들고 위아래를 비웠습니다.

**카메라가 절대값입니다.** 다른 히어로는 엔진이 알아서 잡은 화면을 배수로
당긴 것인데, 2.3 km 짜리 다리를 엔진이 알아서 잡으면 화면 가운데 선 하나가
되고 그 어떤 배수도 썸네일이 아닙니다.

**바닥판이 주황입니다.** 엔진 기본값도 영상의 도장도 바닥판을 거의 흰색으로
두는데, 썸네일 크기에서는 그게 **흰 리본에 주황 막대 둘**로 보입니다. 모두가
아는 그 다리는 끝에서 끝까지 주황입니다. 그래서 바닥판과 트러스를 주황 위로
올리지 않고 주황 **안으로** 내렸고, 주탑이 제일 밝은 것으로 남습니다.

글자는 대각선이 비워 주는 **왼쪽 아래 구석**에 놓입니다. 씌우는 것도 직선
가장자리의 장막이 아니라 부드러운 방사형 워시입니다 — 풀블리드 그림 위의
직선 경계는 그림 위에 띠를 얹은 것으로 보입니다.

글자는 `3D BIM MODELING` / **`GOLDEN GATE BRIDGE`** / `by PLATE3D` 입니다.

첫 판은 `THREE SECTIONS` / `2,219 MEMBERS` 였습니다. **그림이 어느 다리인지
이미 말한다**는 전제였는데, 멈춰서 본 사람에게는 맞고 **스크롤하는 사람에게는
아닙니다.** 교습 편들이 제목을 되풀이하지 않는 것은 두 줄뿐인 자리에 같은 말을
두 번 쓰는 것이 낭비이기 때문이고, 유명한 구조물 편은 반대입니다 — **이름이
멈추는 이유**이고, 사람들이 검색하는 말도 그것입니다. THREE SECTIONS 를
검색하는 사람은 없습니다.

세 번째 줄은 작고 흐립니다. 앞의 두 줄이 멈춰 세운 다음에 읽는 줄이라, 더
크면 이름과 싸웁니다. `by PLATE3D` 는 영상의 첫 카드(`BY PLATE3D`)와 같은
말이고, 목록에서도 영상에서도 같은 자리에 섭니다.

### 높은 것은 대각선이 아니라 옆으로 세웁니다

```
node mkthumb.js eiffel
```

골든게이트에서 나온 것은 전부 **다리가 가로로 2.3 km 라서** 나온 것입니다.
가로 화면에 가로 물건이니 모서리에서 모서리로 눕혔고, 대각선이 비워 준
구석을 글자가 가져갔습니다. **300 m 탑은 정반대 문제**입니다 — 탑은 화면의
**높이**를 채우고 좌우가 통째로 빕니다. 가운데 두면 글자가 갈 데가 탑 위밖에
없습니다.

그래서 탑을 **가로 3분의 2 지점**에 세우고 왼쪽을 글자가 씁니다. 씌우는
워시도 구석이 아니라 **왼쪽 변**에서 들어옵니다. 글자를 아래 구석으로
내리면 탑에서 제일 넓은 부분, 즉 다리 밑동 위에 앉습니다.

**옮기는 것은 카메라입니다.** 조준점을 화면 왼쪽으로 108 m 밀면 카메라가
탑의 왼쪽을 보게 되고 탑이 오른쪽으로 갑니다. 방위각 a 에서 화면 왼쪽은
월드 `(sin a, −cos a)` — az −40 이면 `(−0.64, −0.77)` 입니다. 첫 판은 이
부호가 반대여서 탑이 34% 에, 글자 밑에 깔렸습니다.

**여기서는 크롭을 아예 끕니다**(`crop: false`). 채도로 강재를 찾는 크롭은
바닥 격자 위의 야무진 물건에 맞는 방법이고 이것에는 안 맞습니다 — 탑의
윗절반은 안티에일리어싱으로 바닥과 구별이 안 되는 색까지 내려가는데 먼
구석의 격자선은 채도가 남아서, 캔버스의 99% 를 돌려주고 그게 탑이라고
했습니다. 렌더가 이미 16:9 이므로 조준이 못 하는 일을 크롭이 대신할 것도
없습니다.

**도장은 영상 것에서 한 스톱 올립니다.** 320 px 짜리 정지 화면은 움직이는
그림이 움직임으로 나르는 것을 색으로 날라야 하는데, 탑은 얇은 부재의
격자라 바닥 쪽으로 흐려집니다.

**층 모듈만 반대로 내립니다.** 층 바닥이 순백으로 나왔습니다 — 글자 다음으로
화면에서 제일 밝은 것이, 주황 탑을 가로지르는 막대 셋. 처음 세운 가설은
"바닥은 플레이트이고 플레이트는 색 스코프가 따로 있다"였고
`setColor('plate', ...)` 는 **아무것도 바꾸지 못했습니다**: 모듈 안의
플레이트는 **모듈 색**을 씁니다(엔진이 moduleId 를 먼저 보고 플레이트
override 까지 가지 않습니다). 처음부터 모듈 색이었고, 위를 향한 납작한 면이라
날아간 것입니다. 세 스톱 내리니 종이가 아니라 따뜻한 색으로 날아갑니다.

**영상의 흰 바닥은 그대로 둡니다.** 1080p 에서 움직이면 그건 층 바닥으로
읽히고, 실제로 층 바닥입니다. 슬래브 셋 때문에 70초짜리 조립 컷을 다시 찍는
것은 남는 장사가 아닙니다.

## 다시 만들기

```
cd plate3d/video/tools
ln -s <scratch>/node_modules node_modules   # playwright-core three polybooljs exceljs ffmpeg-static
node prep_ggb.js          # 워크북 86장 + DXF + 도면 페이지 (약 3분)
node mkcards_ggb.js       # 자막·타이틀·아웃트로 카드
node rendercards_ggb.js   # 카드 → PNG/JPEG
node shoot_ggb.js         # 촬영 — 950여 스틸, 약 30분
node assemble_ggb.js      # 조립
```

`v_font.css`(Inter 를 data URI 로) 가 있으면 쓰고, 없으면 시스템 서체로
떨어집니다. 생성물과 mp4 는 저장소에 넣지 않습니다.
